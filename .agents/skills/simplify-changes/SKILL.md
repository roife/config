# Simplify Changes

让维护者能沿项目惯用的写法读懂相同的行为。以调用方仍能依赖的契约和减少的理解成本判断一次化简是否值得。

## 范围

从请求和上下文确定文件、模块或 diff。“化简你的修改”限于当前任务的变更，区分同文件内其他人的修改；空 diff 不意味着改扫全仓。只有范围存在实质歧义且无法从上下文判断时才澄清。

按请求区分建议与修改；已有执行授权就直接完成，不在分析后再次询问是否实施。为理解行为按需读取调用者，不扩展为无关重构。

## 化简判断

- 先看相邻实现、真实调用入口和已有工具。复用前核对输入范围、执行顺序和异常传播。对支持旧数据、重试或并发的路径，再核对相应的状态变化。
- 纯转发、重复解析和回调绕行可以直接消除。保留表达领域含义或所有权的抽象。合并后若要靠嵌套条件或缩短命名才能读下去，改用显式步骤。
- 删除兼容分支前核对支持范围；没有本地调用者不能证明公开 API 或动态入口无人使用。
- 根据类型、调用契约或实际实现判断防御逻辑是否冗余。保留外部输入、I/O、取消和资源释放所需的处理；不靠吞异常或删失败测试制造通过。

发现行为缺陷时，按已有修复授权处理，不能把行为改变称作等价化简。没有有依据的改进时可以零修改结束。

## 验证与交付

优先用现有调用入口和相关测试验证等价性。用户或仓库要求测试，或现有用例漏掉这次变更的具体回归风险时，再补对应测试。检查最终 diff 的范围，说明哪条调用路径变得更容易理解、执行了哪些验证，以及仍影响结论的缺口。

维护或追溯设计时可读 [来源与取舍](references/sources.md)。
